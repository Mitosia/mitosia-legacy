# Mitosia Project Rules

Read [docs/tech-stack.md](docs/tech-stack.md) (stack decisions and rationale) and [docs/sprint-plan.md](docs/sprint-plan.md) (build sequence) before architectural work. Record new durable decisions in this file.

## Git workflow

- **Never commit or push directly to `main`.** All work lands through a pull request: branch → commit → push → open PR → CI green → merge. This holds for docs and one-line fixes too.
- Branch names: `feat/…`, `fix/…`, `chore/…`, `docs/…`.
- CI (lint, typecheck, build) must pass before merge. Merging to `main` deploys to staging, so a red build is a broken staging environment.
- `production` is promoted only by fast-forwarding from `main` — never a direct commit, never a PR target for feature work.

## Environments and deployment

- `main` = staging → auto-deploys to https://staging.mitosia.cloud (Dokploy, Dockerfile build on the VPS).
- `production` = prod → https://app.mitosia.com. Promote by fast-forwarding `production` to `main` — never commit directly to `production`.
- The `mitosia.com` apex is reserved for the future marketing site; the product lives at `app.mitosia.com`. `mitosia.com` DNS goes behind Cloudflare (CDN/WAF) when prod ships; `mitosia.cloud` stays on plain Hostinger DNS deliberately (simple Let's Encrypt issuance).
- `mitosia.cloud` is the infra domain: Dokploy panel at dokploy.mitosia.cloud; wildcard `*.mitosia.cloud` already points at the VPS, so new services need zero DNS work.
- Dokploy layout: one project `mitosia` containing two environments — `staging` (app + its own Postgres service, tracks `main`) and `production` (app only, tracks `production` branch, database on Neon). Services are isolated per environment; never point a staging service at production data.
- VPS: Hostinger KVM 8 at 72.61.169.154, SSH alias `mitosia-vps` (key auth). ufw allows only 22 (rate-limited), 80, 443. The Dokploy panel's port 3000 must stay unpublished — Docker-published ports bypass ufw, so re-verify after any Dokploy self-update.
- Secrets are per-environment: separate `BETTER_AUTH_SECRET` and `DATABASE_URL` for dev/staging/prod, injected as runtime env in Dokploy — never baked into the Docker image or committed. Staging DB: Dokploy-provisioned Postgres on the VPS. Production DB: Neon (managed, PITR).

## Local development

- Dev Postgres: `docker compose up -d`, host port **55433**. Do not "simplify" this to 5432/5433: 5432 is a native Homebrew Postgres, and the IPv4 side of 5433 belongs to a Podman VM hosting Postgres for **kaera** (a separate project — never stop or modify the Podman machine).
- Dev object storage: MinIO from the same compose file — S3 API on **55490**, console on **55491**, bucket `mitosia-media` auto-created. Deployed environments use Cloudflare R2 through the identical S3 adapter (`lib/storage`); only `STORAGE_*` env changes. R2 buckets need a CORS rule exposing `ETag` or browser multipart uploads cannot complete.
- Dev server runs on port 3001 (`.claude/launch.json`); `BETTER_AUTH_URL` must match the served origin or logins fail origin checks. The same file defines `mitosia-prod-local`: the standalone production build served Dockerfile-style on 3001 (run `pnpm build` first). Before calling a browser-observable bug "dev-only", reproduce against it — the waveform blank-strip bug wore that label for a sprint and was in production the whole time.
- `.env` is gitignored; update `.env.example` whenever env vars change.
- The ingest pipeline shells out to **ffmpeg/ffprobe** — required on dev machines (`brew install ffmpeg`) and installed in the Docker image. It must be the **same minor everywhere** (8.1.x today); `pnpm check:ffmpeg` tells you whether yours is. The e2e suite needs docker compose services up plus ffmpeg.

## Media pipeline (S2 decisions)

- Storage keys: `org/{orgId}/client/{clientId}/source/{sourceId}/…` — the `org/` prefix is the authorization boundary. Media reaches the browser only through `/api/media/[...path]`, an authenticated same-origin streaming proxy that rejects keys outside the caller's active org. No public/presigned URLs in the client; the R2+CDN signed-URL path arrives with client delivery (S18).
- Uploads resume across browser sessions, and that rests on Uppy file state being the *only* place upload identity lives (decision 2026-08-11). The source id goes into `file.meta.sourceId` and never into a closure: `@uppy/golden-retriever` persists file state — meta plus `@uppy/aws-s3`'s own `s3Multipart` key/upload id — to localStorage, so a reloaded page still knows which `/api/uploads/[sourceId]/…` routes to talk to and `listParts` can skip what storage already holds. The Uppy instance id is namespaced per project (it keys both Golden Retriever's stores and Uppy's file ids). Browsers cannot restore a multi-GB `File`, so files over ~10 MB come back as ghosts and the user re-selects them; re-selecting reproduces the same Uppy file id (name + type + size + lastModified), which is what reconnects file to upload — don't add anything to the id derivation. Restored uploads are probed against the parts endpoint before being trusted, because the multipart upload behind them may be gone. `e2e/upload-resume.spec.ts` guards the whole path with a >10 MB fixture; it fails on the pre-fix code.
- Abandoned uploads are reaped, not left as ghosts: `reapStaleUploads()` (lib/uploads.ts) marks `uploading` sources failed and aborts their storage-side multipart upload after `UPLOAD_IDLE_TTL_HOURS` (lib/upload-window.ts) of idleness — the same window the browser's resume state expires on, deliberately. It is *idle* time: signing a part (`POST …/parts`) bumps `updated_at` (`touchUpload`), which is the only trace an in-flight upload leaves on the app server, so a slow 20 GB upload never trips it. **Listing** parts must never touch it — a restored page probes uploads it may abandon again, and letting that count as liveness makes an abandoned upload immortal (it also races the sweep, which is how the bug was found). The sweep is scheduled from the project page's render via `after()` rather than a cron, because that page is where the ghosts appear and Trigger.dev is not wired up everywhere; it fires only when the page's own query flagged a row via `isStaleUpload`, so healthy uploads and the 3.5 s poller cost nothing. R2's "Default Multipart Abort Rule" is the backstop for what the sweep never sees — `pnpm check:abort-rule` asserts it.
- Ingest runs through one seam: `enqueueIngest()` (lib/ingest.ts). With `TRIGGER_SECRET_KEY` set it triggers the durable Trigger.dev task (`trigger/ingest-source.ts`); without it the pipeline runs in-process after the response (dev fallback — dies with the server, documented, not for real workloads). Pipeline steps and their ffmpeg invocations live in `lib/media/`; the claim step makes re-enqueues and retries idempotent.
- Every artifact row carries its own `size_bytes`, written at upload time (`ArtifactUpload.sizeBytes` is required, not optional), and the artifacts `storage_bytes` ledger entry is **summed back out of those rows** inside the finalize transaction — one number, not a parallel tally that can drift. The single `hls_master` row accounts for the entire ladder (every playlist and segment under `hls/`), which is what makes that sum equal the real stored footprint; don't "fix" it to the size of `master.m3u8`. Both properties are asserted against the database in the ingest e2e — this is invisible in the UI, and `size_bytes` sat NULL on every row for a whole sprint without anything looking wrong.
- Upload resumability has **two independent halves, and the browser's half is destructible**. Golden Retriever restores the file list, source id and multipart state from localStorage/IndexedDB — the fast path — but files over 10 MB come back as ghosts, and dismissing that recovery card (or clearing site data, or switching browser) drops the state entirely. Re-adding the same file then opened a *second* multipart upload: observed on staging with the 2 GB exit-test source, which stranded 115 MB of parts under a duplicate row stuck at `uploading` while the UI promised the upload would carry on. So the server also matches on what it can see for itself — `findAdoptableUpload` (`lib/uploads.ts`): same project, filename and byte size, still `uploading`, and quiet for longer than `UPLOAD_ADOPT_GRACE_SECONDS`. That grace window is the guard against adopting an upload another tab is actively writing, and it works because `touchUpload` stamps `updated_at` on every signed part. Client-side adoption runs in an Uppy **pre-processor**, not a `file-added` handler: pre-processors are awaited before any uploader starts, so seeding `s3Multipart` (which is what puts `@uppy/aws-s3` on its `listParts` branch) always wins the race against a fast click. The same check also runs inside `POST /api/uploads`, so a duplicate row is unreachable rather than merely unlikely. Both paths are covered in `e2e/` — `upload-resume.spec.ts` for the browser half, `upload-adopt.spec.ts` for the server half — and the second one only proves anything with a fixture over 10 MB.
- Usage ledger (`usage_ledger`) is append-only **by policy shape**: it has only SELECT and INSERT RLS policies, so UPDATE/DELETE are database-denied even in-org. Writers must be idempotent via `correlation_id` (unique); corrections are compensating entries. Anything metered writes to the ledger in the sprint it ships — never retrofitted.
- Backfilling a metering column reads the **objects**, never the ledger: `pnpm backfill:artifact-sizes [--dry-run]` (scripts/backfill-artifact-sizes.ts) sizes historical artifacts from storage, org by org through `withOrgScope` so it needs no superuser and no policy exemption. It reports any source where the summed artifact bytes disagree with the ledger and writes nothing to `usage_ledger` — a correction there is a compensating entry, and a human's call.
- **One ffmpeg minor everywhere — 8.1.x — pinned in three places** (decision 2026-08-11). An ffmpeg option that doesn't exist is a *hard* failure: ffmpeg refuses to start and every ingest breaks. CI used to install Ubuntu's apt ffmpeg (6.1.1) while the image installs Alpine's (8.1.2), so CI could neither exercise the ffmpeg 8 behaviour `lib/media/` is written around nor accept an ffmpeg 8 flag — `-reconnect_max_retries`, verified on staging and macOS, died in CI with "Option not found" and was dropped to unblock (PR #23). The **image is the source of truth**: the Dockerfile runner pins the Alpine *release* (`node:24-alpine3.24`, not the floating `node:24-alpine`) because Alpine carries one ffmpeg minor per release for its whole life, and CI installs that same minor as a checksummed static build (a pinned immutable BtbN release asset) because no Ubuntu release ships it. Enforcement is `scripts/check-ffmpeg-version.mjs` — it holds the expected minor and runs both in the CI e2e job and inside the Docker build, so whichever side drifts fails loudly; `pnpm check:ffmpeg` runs it on your machine. Rejected alternatives: running e2e inside the app image (it has no dev deps, and Playwright ships no musl browsers, so Alpine is a dead end), and `apk add ffmpeg=<exact>` (Alpine prunes superseded versions, so the pin breaks at the next patch bump).
- **Version-support rule for ffmpeg flags:** a new flag, filter or filter option may only be used if it exists in the pinned minor — check it against 8.1.x (`ffmpeg -h full`, or `docker run --rm node:24-alpine3.24 sh -c 'apk add -q ffmpeg && ffmpeg -h full'`), never against whatever your Mac happens to have. Moving to a newer ffmpeg is its own PR that bumps all three pins in one commit — `EXPECTED_MINOR` in the check script, the Alpine tag in the Dockerfile, the release/asset/sha256 in ci.yml — and re-runs the ingest e2e. Trigger.dev is the one surface this pin does **not** cover: its `ffmpeg()` build extension installs Debian apt ffmpeg (5.1.x) into the deploy image, so pin that too before `TRIGGER_SECRET_KEY` ever moves ingest off the in-process runner.
- **The ladder reports progress; every other step is short enough not to.** `-progress pipe:1` on the HLS ffmpeg run feeds a throttled write (10s) to `source.ingest_progress` (0–1, null when a step has nothing finer to say than its name), rendered as "Preparing playback 42%". A two-hour source spends ~30 minutes in that one step, and while it reported nothing the badge never changed *and* `updated_at` never moved — a healthy ingest was indistinguishable from a hung one in both the UI and the database, and got reported as stuck. Progress writes are best-effort and swallow their errors: a cosmetic signal must never fail a transcode. `parseProgressSeconds` reads `out_time_us` and deliberately ignores `out_time_ms`, which is microseconds too despite the name — matching it as milliseconds reports 1000× fast.
- **Trigger.dev gets the pinned ffmpeg too, via a custom build extension** (`pinnedFfmpeg` in trigger.config.ts). The bundled `ffmpeg()` extension installs Debian apt ffmpeg (5.1.x) and its only alternative is a floating git build; neither is the pinned minor. This is not cosmetic — `-reconnect_on_network_error` landed in 6.1, so the first thing setting `TRIGGER_SECRET_KEY` would have done is break every ingest on 5.1, on the runtime whose whole purpose is making ingest more reliable. The asset coordinates live in `scripts/ffmpeg-pin.mjs` and are consumed by both CI and the Trigger image; the deploy layer re-runs `check-ffmpeg-version.mjs` so a drifted pin fails the deploy, not the first upload.
- ffmpeg 8 quirks encoded in `lib/media/`: mjpeg outputs need `format=yuvj420p` (limited-range YUV is rejected), and `fps=1/N` needs `:round=up` or sources shorter than N seconds emit zero thumbnails. Don't "clean up" those filter args.
- **Remote ffmpeg inputs go through `inputArgs()` (`lib/media/ffmpeg.ts`), and every transcode is duration-verified before it can reach `ready` (`lib/media/verify.ts`).** ffmpeg's HTTP reader treats a mid-transfer disconnect as end-of-file: it finalizes a **valid but truncated** output and exits 0, so with `-v error` nothing looks wrong anywhere. The exposure is read *duration*, not file size — the CPU-bound HLS ladder holds one connection open for the whole transcode (~28 min for a 2h source at 0.26× realtime, ~1.2 MB/s) while the audio step drains the same object in ~2 min and is unaffected. The S2 exit test produced a source marked `ready` carrying 4189s of 7200s of video (58.2%) on all three rungs, because probe had written the true 7200s to the row and nothing ever compared the two: the details pane read 2:00:00 from the database while the player read 69:48 from the playlist. Sources under ~5 minutes finish the read in seconds, which is why this survived all of S2. Never write a bare `-i url`, and never drop the duration assertions — reconnect flags lower the odds, the assertions are what keep a miss from reaching users silently.
- Rendition ladder (`lib/media/hls.ts`) follows platform practice deliberately: native-resolution top rung (≤1080p, capped CRF per Apple's peak≤200%-of-average VOD rule, `fast` preset) over 720p/360p proxies, 2s keyframes, High profile, 1.5× caps for >40fps sources; the player starts at the top rung. The 234p–480p cellular rungs and multi-codec (VP9/AV1) are deferred until client delivery (S18) — don't add them to the review path.
- The source player (`components/sources/source-player.tsx`) is **Video.js v10 React** (`@videojs/react`, packaged `VideoSkin` + `HlsJsVideo`; hls.js is its internal engine — decision 2026-08-10, v8 is legacy/maintenance-only). Three hard-won rules, in its header comment — change them only with the e2e green: client-only mount (placeholder during SSR/hydration); peaks bound through a **passive `PlayerAdapter`**, never its default `MediaElementPlayer` (the engine attaches MediaSource at mount and StrictMode double-mounts it — `MediaElementPlayer.init` inspecting the element mid-churn either `load()`s a revoked single-use blob URL or rejects on a transient media error and hides the waveform; the adapter never loads and never inspects source state, so peaks-vs-engine ordering stops mattering and `src` needs no gating); and `playedWaveformColor` applied on `durationchange`, never at `Peaks.init` (peaks.js 4.0 freezes the played/unplayed boundary with the init-time duration — NaN before metadata — which left the whole strip permanently blank on load, identically in dev and production builds — reported upstream as [bbc/peaks.js#574](https://github.com/bbc/peaks.js/issues/574), so revisit this workaround when it is fixed). Startup quality rides `config.hlsJs.abrEwmaDefaultEstimate` (exceeds every ladder top rung → auto start level = top rendition); the config object must keep a stable identity or the engine reloads. The ingest e2e guards these: full-document-load for the SSR half, plus nonblank-pixel and played/unplayed-color assertions on the overview canvas — canvas *visibility* alone is not a render check and let the blank strip ship. Peaks.init additionally waits for the overview container to have layout (`waitForLayout`) — zero-width init (hidden tab, prerender) throws and used to hide the waveform permanently.
- Waveform peaks (`lib/media/peaks.ts`) must span the **media** duration, not the audio stream: sources whose audio ends early are padded with silent buckets, and `samples_per_pixel` scales with duration to target a ~4096px native width. Both are load-bearing for the overview timeline: peaks.js maps pixels to time through the data's implied duration and cannot upsample, so audio-length or too-short data desynchronizes the waveform x-axis from the video timeline (wide windows: truncated-looking waveform; narrow: playhead pegged early). Don't regress to a fixed `samples_per_pixel`.

## Tenancy and RLS (load-bearing security rules)

- Tenant-owned tables (anything with `organization_id`) get `ENABLE` + `FORCE ROW LEVEL SECURITY` and an org-isolation policy **in the same migration that creates them**, and an entry in `tests/rls-isolation.test.ts`.
- App code touches tenant tables **only** inside `withOrgScope()` (`lib/db/tenant.ts`), with the org id taken from `requireOrg()` — never from user input.
- The app's `DATABASE_URL` role must **never** be a superuser or table owner: superusers bypass RLS silently, and the Docker image's `POSTGRES_USER` is a superuser. The app connects as `mitosia_app`; `MIGRATE_DATABASE_URL` carries the owner connection used only by drizzle-kit and the container entrypoint. This applies to **CI too**: the e2e job creates `ci_app` (see ci.yml) — running the e2e app as the `ci` superuser silently disabled RLS and let a Playwright retry walk into a previous attempt's tenant (PR #16).
- Foreign-key checks do not consult RLS. Before inserting a child row, re-read the parent inside the org scope (see `assertVisible` in `lib/actions/hierarchy.ts`) so a cross-tenant parent id can never be attached.
- Tests: `TEST_DATABASE_URL` must point at a disposable database (the suite wipes it); run with `pnpm test`.

## UI (hard rule)

- **Never build UI components from scratch.** Before writing any UI, search the shadcn registry for an official component or block that fits (`pnpm exec shadcn add <name>`; blocks like `sidebar-07`, login/dashboard blocks, etc.) and adapt it. Composing registry primitives into domain components is fine; hand-rolling layout/navigation/form primitives that the registry already provides is not.
- **When adapting a registry block, keep its structural wrappers.** Base UI parts are context-coupled: `Menu.GroupLabel`/`DropdownMenuLabel` must stay inside a `Menu.Group`/`DropdownMenuGroup`, etc. Dropping a wrapper compiles fine and then crashes at runtime when the menu opens (e.g. "MenuGroupContext is missing"). This is exactly why the registry-first rule exists.
- **Interactive UI must be exercised by an e2e test.** Any menu, dialog, popover, or dropdown that can be opened gets a Playwright test in `e2e/` that opens it and asserts no `pageerror`. A visual/manual sweep is not sufficient — Base UI context crashes only fire on interaction. Run with `pnpm e2e` (dev server on 3001; `BETTER_AUTH_URL` must match that origin).
- **Two e2e suites, and they catch different things.** `pnpm e2e` runs against `next dev`; `pnpm e2e:prod` (`playwright.prod.config.ts`, `e2e-prod/`, port 3002) runs against the standalone production build via `scripts/serve-standalone.mjs` and needs a `pnpm build` first. Dev mode cannot see hydration mismatches (React reports them as warnings, not the minified runtime error), and a mismatch shipped to production behind that gap. **Guard hydration and SSR behaviour by asserting on the server-rendered HTML**, not by sweeping for `pageerror`: mismatches are timing-dependent, and the sweep demonstrably passes on a build with the known regression restored while the SSR assertion fails immediately.
- The only exception is genuinely novel domain UI with no registry equivalent (e.g. the campaign canvas, transcript editor) — and even those must be built out of registry primitives wherever possible. Note the exception in the PR description when it applies.
- This registry uses the Base UI variant: composition is via the `render` prop, not `asChild`. Icons come from `@hugeicons/core-free-icons` (ESM-only — check names with an ESM import, not `require`).

## Conventions

- The auth schema is generated: `pnpm db:auth:generate` (Better Auth CLI). Never hand-edit `lib/db/schema/auth.ts`.
- Schema changes ship as migrations: `pnpm db:generate` to author them, `pnpm db:migrate` to apply locally. No `drizzle-kit push` against shared databases.
- Deployed environments migrate themselves: `docker-entrypoint.sh` runs the bundled `scripts/migrate.ts` (advisory-locked, idempotent) before starting the server, and a failed migration aborts the container so the deploy fails loudly. Never run migrations during `docker build` — the image must stay environment-agnostic and build-time has no real database.
- `components/ui/**` is vendored shadcn registry output — lint-exempt (see biome.jsonc), regenerated via the shadcn CLI, not hand-maintained.
- `proxy.ts` performs optimistic redirects only. Authorization lives in server components and route handlers, never in the proxy.
