# Mitosia Project Rules

Read [docs/tech-stack.md](docs/tech-stack.md) (stack decisions and rationale) and [docs/sprint-plan.md](docs/sprint-plan.md) (build sequence) before architectural work. Record new durable decisions in this file.

## Git workflow

- **Never commit or push directly to `main`.** All work lands through a pull request: branch → commit → `pnpm pr:verified -- <gh-pr-create-args>` → required Actions-owned `checks` proof green → merge. This holds for docs and one-line fixes too.
- Branch names: `feat/…`, `fix/…`, `chore/…`, `docs/…`.
- **PR validation is local while Mitosia has one developer** (decision 2026-08-29; reverse this before adding a collaborator). `pnpm ci:local` requires a clean commit, starts the compose services, creates a unique disposable database/bucket and non-superuser RLS app role, then runs frozen install → Ultracite → ffmpeg pin → Vitest/RLS → Next build/typecheck → production hydration e2e → dev-suite e2e. It records success against the exact SHA outside the worktree and cleans the disposable resources on success or failure. The installed pre-push hook reruns the gate unless that exact SHA already has a receipt, rejects another ref's SHA, and forbids direct `main`/`production` pushes. `pnpm push:verified` pushes only after the gate and publishes the `local-ci` commit status; `pnpm pr:verified -- <args>` does that before opening the PR. GitHub runs only a tiny provenance job under the established Actions-owned `checks` context (no checkout/install/tests), and strict admin-enforced branch protection requires it. Reusing `checks` kept already-green PRs mergeable during the transition; the former `e2e` context is no longer required after this policy lands. A raw/`--no-verify` push cannot become mergeable without an exact-SHA status. Re-enable independent GitHub-hosted validation when the project gains another committer; a developer-authored local attestation is an intentional solo-project cost tradeoff, not a team trust boundary.
- `production` is promoted only by fast-forwarding from `main` — never a direct commit, never a PR target for feature work.

## Environments and deployment

- `main` = staging → auto-deploys to https://staging.mitosia.cloud (Dokploy, Dockerfile build on the VPS).
- `production` = prod → https://app.mitosia.com. Promote by fast-forwarding `production` to `main` — never commit directly to `production`.
- The `mitosia.com` apex is reserved for the future marketing site; the product lives at `app.mitosia.com`.
- **User-facing hostnames go behind Cloudflare before production, and the origin is then locked to Cloudflare's ranges** (decision 2026-08-11; runbook in [docs/cloudflare-origin.md](docs/cloudflare-origin.md), `scripts/cloudflare-origin-lock.sh`). This replaces the earlier "`mitosia.cloud` stays on plain Hostinger DNS for simple Let's Encrypt issuance" note, which was reasonable until an ISP disproved its premise: Reliance Jio could not route to the VPS at all — every port timing out, traceroute dying inside Jio's own network at `136.232.253.36` — while Airtel and other networks reached the same address normally, with the box healthy throughout (4 days uptime, load 0.01). **Nothing on the server can fix that**; the problem is how one ISP routes to one IP, Jio is India's largest ISP, and Hostinger recycles addresses. Users must not connect to the origin IP at all. **Done 2026-08-17**; what the cutover settled, where it departed from the plan above:
  - **Certificates: two live resolvers, and a Cloudflare Origin Certificate was rejected.** `letsencrypt` (HTTP-01) issued and still renews the **per-host** certs that `staging` and `dokploy` actually serve — it is load-bearing, not legacy. `letsencrypt-dns` (DNS-01) issues the wildcard `*.mitosia.cloud`, wired as `tls.stores.default.defaultGeneratedCert`, so it covers only hostnames with no cert of their own and a new subdomain works with zero issuance. It is a default rather than a per-router change because Dokploy regenerates the `certresolver=letsencrypt` labels on every deploy. Separate storage files (`acme.json` / `acme-dns.json`) — two resolvers must never share one. HTTP-01 is the challenge a CDN can break, but **verified 2026-08-18 that `/.well-known/acme-challenge/` still reaches the origin through Cloudflare** (404 from Traefik, `cf-cache-status: DYNAMIC`, no redirect); re-probe it before adding any redirect/WAF/cache rule matching that path, or renewals fail ~60 days later. An **Origin Certificate was considered and never installed**: trusted by Cloudflare only, so it would break any path reaching the origin outside the proxy — including the grey-cloud fallback. The cost of DNS-01 is a scoped `CF_DNS_API_TOKEN` (Zone:DNS:Edit, this zone only) in Traefik's env. SSL mode is **Full (strict)**, never "Flexible".
  - **The Dokploy panel is proxied, and behind Cloudflare Access.** The plan said leave it unproxied so the recovery tool is not behind the thing that might break. That reasoning was sound but aimed at the wrong recovery path: leaving it unproxied leaves the origin IP reachable, which is the whole problem, and **SSH on port 22 is the real recovery path** — the origin lock only writes to `DOCKER-USER` and never touches `INPUT`, so a broken Cloudflare cannot lock you out of the box. Access policies: `Rajesh only` (Allow → my email) on the panel, plus **Bypass → Everyone on `/api/deploy` and `/api/webhook`**, because GitHub's webhook cannot authenticate. Login is the built-in **Cloudflare** identity provider (the account's own MFA), not a one-time email PIN.
  - **Any other automation against the Dokploy API now hits the Access login**, not the API — a 302 to `*.cloudflareaccess.com`, which a script reads as a strange success. Give automation a Cloudflare **service token** and a Service Auth policy; do not widen the bypass paths.
  - Traefik needs `forwardedHeaders.trustedIPs` set to Cloudflare's ranges only, or every client appears to come from Cloudflare and rate limits and audit logs silently record the wrong address. Better Auth reads `cf-connecting-ip` first (`lib/auth.ts`).
  - `pnpm check:traefik` asserts the whole shape against the live box (trustedIPs, both resolvers, the default cert, expiry ≥21 days); exit 2 means the host was unreachable, not that config drifted.
- `mitosia.cloud` is the infra domain: Dokploy panel at dokploy.mitosia.cloud; wildcard `*.mitosia.cloud` already points at the VPS, so new services need zero DNS work.
- **The Trigger.dev worker deploys from its own path-filtered workflow, not by hand** (decision 2026-08-24, revised 2026-08-29): `.github/workflows/deploy-trigger.yml` starts `trigger.dev deploy` immediately when a protected merge to `main` changes `trigger/**`, broad `lib/**`, the Trigger build/ffmpeg inputs, database contract, or dependency files. Strict branch protection already requires the exact up-to-date PR head's local validation proof; repeating the full suite after merge would delay the worker without protecting the independently deploying Dokploy app. The broad `lib/**` filter deliberately prefers an occasional unnecessary worker build over a stale task from a brittle import allowlist; UI-only `app/**`/`components/**` merges do not rebuild it. Deployment still requires the `TRIGGER_PROJECT_REF` repo **variable** (opt-in switch — job skips while unset) and `TRIGGER_ACCESS_TOKEN` **secret**; variable-without-secret fails loudly. The CLI version is derived from `@trigger.dev/sdk` in package.json — never `@latest`; CLI/SDK drift breaks deploys (S3 lesson). Until the switch is set, deploys stay manual with the same pin: `npx trigger.dev@<sdk version> deploy` (docs/media-infra-setup.md). Remember the app image and worker image are **two deploy targets**.
- Dokploy layout: one project `mitosia` containing two environments — `staging` (app + its own Postgres service, tracks `main`) and `production` (app only, tracks `production` branch, database on Neon). Services are isolated per environment; never point a staging service at production data.
- VPS: Hostinger KVM 8 at 72.61.169.154 (Mumbai), SSH alias `mitosia-vps` (key auth). **There is no ufw** — installing `iptables-persistent` removes it, and the firewall is now raw iptables saved to `/etc/iptables/rules.v{4,6}` (`netfilter-persistent save` after every change, or it is lost on reboot). Two independent layers, and they live in different chains for a reason: SSH rate limiting (6 new connections per 30s, v4 **and** v6) sits in `INPUT`, while the Cloudflare origin lock sits in `DOCKER-USER`. **Traffic to Docker-published ports never traverses `INPUT`** — it is DNAT'd through Docker's own chains — so an INPUT rule for 80/443 is inert and an INPUT-based tool like ufw cannot restrict them at all. The Dokploy panel's port 3000 must stay unpublished for the same reason: publishing it would bypass any host firewall entirely.
- Secrets are per-environment: separate `BETTER_AUTH_SECRET` and `DATABASE_URL` for dev/staging/prod, injected as runtime env in Dokploy — never baked into the Docker image or committed. **Staging DB is Neon** (`mitosia` database, **ap-southeast-1 / Singapore**, moved off the VPS 2026-08-11 so Trigger.dev cloud workers can reach it — first placed in us-east-2 by reading a `time_connect` comparison that was confounded by Happy Eyeballs, then moved 2026-08-17 once the VPS's own location was checked: Mumbai→Singapore is 4.3× faster than Mumbai→Ohio, and Mumbai was not on Neon's region list); production DB will be a *separate* Neon project, not another branch of the same one — same-project branches put "reset from parent" one click away from copying real data into staging.
- **An env change only reaches the container on a deploy that changes the image, and a container that then exits non-zero reverts it invisibly.** Two behaviours compound. Dokploy regenerates the swarm service's env from its own record, but only as part of an image-changing deploy: `application.update` / `saveEnvironment` persist to the record and change nothing running, and `application.deploy` on an unchanged image is a no-op at the service level (as is `stop`→`start`, which only scales to 0/0 and keeps the spec). Then Swarm's `UpdateConfig.FailureAction=rollback` restores the **entire previous spec, env included**, when the new task exits non-zero — so an env change that breaks startup looks exactly like an env change that was never applied. That cost hours during the Neon cutover: the new env was correct, the container could not reach the database, and every layer reported success (`200` from the API, `done` in the deployment list, "converged" from `docker service update`). **Verify against the running service, never the API response** — `docker service inspect <svc> --format '{{range .Spec.TaskTemplate.ContainerSpec.Env}}{{println .}}{{end}}'` — and when a deploy "succeeds" but nothing changed, read the dead container's log: `docker logs $(docker ps -a --filter name=<svc> --format '{{.ID}} {{.Status}}' | grep -i exited | head -1 | cut -d' ' -f1)`. A value set only with `docker service update --env-add` (not saved to the record) survives until the next image-changing deploy, then vanishes.
- Port 22 is rate-limited (6 new connections per 30s), so SSH *polling loops* lock you out of the VPS for minutes. Poll over HTTPS or against the database; keep SSH to single checks.

## Local development

- Dev Postgres: `docker compose up -d`, host port **55433**. Do not "simplify" this to 5432/5433: 5432 is a native Homebrew Postgres, and the IPv4 side of 5433 belongs to a Podman VM hosting Postgres for **kaera** (a separate project — never stop or modify the Podman machine).
- Dev object storage: MinIO from the same compose file — S3 API on **55490**, console on **55491**, bucket `mitosia-media` auto-created. Deployed environments use Cloudflare R2 through the identical S3 adapter (`lib/storage`); only `STORAGE_*` env changes. R2 buckets need a CORS rule exposing `ETag` or browser multipart uploads cannot complete.
- Dev server runs on port 3001 (`.claude/launch.json`); `BETTER_AUTH_URL` must match the served origin or logins fail origin checks. The same file defines `mitosia-prod-local`: the standalone production build served Dockerfile-style on 3001 (run `pnpm build` first). Before calling a browser-observable bug "dev-only", reproduce against it — the waveform blank-strip bug wore that label for a sprint and was in production the whole time.
- `.env` is gitignored; update `.env.example` whenever env vars change.
- **`TRIGGER_SECRET_KEY` in `.env` silently disables local ingest.** `enqueueIngest()` switches to Trigger.dev the moment that variable is non-empty, so without `npx trigger.dev@latest dev` running, every upload sits at `uploaded` ("Queued") forever — no error, nothing in the log. It fails the ingest e2e the same way (`expected "ready", received "uploaded"`), which looks like a pipeline regression and is not one. Either keep the dev worker running or prefix the run: `TRIGGER_SECRET_KEY= pnpm e2e` (shell env wins over `.env` in Next).
- The ingest pipeline shells out to **ffmpeg/ffprobe** — required on dev machines (`brew install ffmpeg`) and installed in the Docker image. It must be the **same minor everywhere** (8.1.x today); `pnpm check:ffmpeg` tells you whether yours is. The e2e suite needs docker compose services up plus ffmpeg.

## Media pipeline (S2 decisions)

- **Source acquisition is upload-first; link ingest is connectors-later, and YouTube extraction is rejected outright** (decision 2026-08-24). Upload stays the primary path because the customer's raw material is the *master* (Zoom/Riverside recording, podcast WAV, 4K export) — a platform link hands the pipeline a re-compressed derivative, and every clip cut from it is a generation worse. Link-based ingest, when it comes, is three different features: (1) direct file URLs + cloud drives (Drive, Dropbox, Zoom cloud recordings) — official APIs, OAuth, where agency clients actually keep masters, and technically cheap since the pipeline already reads input over HTTP (`inputArgs()` + duration verification); (2) Vimeo for the owner's own videos via its official download API — same OAuth-connector shape; (3) YouTube — **do not build**: there is no official download API even for channel owners, so the only route is yt-dlp-style extraction, which violates YouTube's ToS (real exposure for a paid agency SaaS), is operationally fragile (extractors break, datacenter IPs — the VPS and Trigger.dev workers — get bot-blocked), and yields the worst-quality source anyway. "Paste a YouTube link" is a support answer — the channel owner downloads their master from YouTube Studio and uploads it — not a feature. Connectors (1)+(2) are slotted at S16 alongside the intake form, where the ClamAV untrusted-input path lands; fetched sources go into R2 under the org prefix and through the identical pipeline. **Scope clarification (Rajesh, 2026-08-25): this rejection is about the PRODUCT — downloading publicly available videos with yt-dlp on a dev machine to source test material for Mitosia during development is fine** (there is often no other way to get realistic long-form sources); such files are uploaded through the normal UI like any master and never wired into ingest as links.
- Storage keys: `org/{orgId}/client/{clientId}/source/{sourceId}/…` — the `org/` prefix is the authorization boundary. Media reaches the browser only through `/api/media/[...path]`, an authenticated same-origin streaming proxy that rejects keys outside the caller's active org. No public/presigned URLs in the client; the R2+CDN signed-URL path arrives with client delivery (S18).
- Uploads resume across browser sessions, and that rests on Uppy file state being the *only* place upload identity lives (decision 2026-08-11). The source id goes into `file.meta.sourceId` and never into a closure: `@uppy/golden-retriever` persists file state — meta plus `@uppy/aws-s3`'s own `s3Multipart` key/upload id — to localStorage, so a reloaded page still knows which `/api/uploads/[sourceId]/…` routes to talk to and `listParts` can skip what storage already holds. The Uppy instance id is namespaced per project (it keys both Golden Retriever's stores and Uppy's file ids). Browsers cannot restore a multi-GB `File`, so files over ~10 MB come back as ghosts and the user re-selects them; re-selecting reproduces the same Uppy file id (name + type + size + lastModified), which is what reconnects file to upload — don't add anything to the id derivation. Restored uploads are probed against the parts endpoint before being trusted, because the multipart upload behind them may be gone. `e2e/upload-resume.spec.ts` guards the whole path with a >10 MB fixture; it fails on the pre-fix code.
- Abandoned uploads are reaped, not left as ghosts: `reapStaleUploads()` (lib/uploads.ts) marks `uploading` sources failed and aborts their storage-side multipart upload after `UPLOAD_IDLE_TTL_HOURS` (lib/upload-window.ts) of idleness — the same window the browser's resume state expires on, deliberately. It is *idle* time: signing a part (`POST …/parts`) bumps `updated_at` (`touchUpload`), which is the only trace an in-flight upload leaves on the app server, so a slow 20 GB upload never trips it. **Listing** parts must never touch it — a restored page probes uploads it may abandon again, and letting that count as liveness makes an abandoned upload immortal (it also races the sweep, which is how the bug was found). The sweep is scheduled from the project page's render via `after()` rather than a cron, because that page is where the ghosts appear and Trigger.dev is not wired up everywhere; it fires only when the page's own query flagged a row via `isStaleUpload`, so healthy uploads and the 3.5 s poller cost nothing. R2's "Default Multipart Abort Rule" is the backstop for what the sweep never sees — `pnpm check:abort-rule` asserts it.
- **Deploying the Trigger.dev task needs the full server env set in the Trigger environment first, or the deploy fails — not the first run.** Trigger *indexes* by importing each task module, and `trigger/ingest-source.ts` pulls in `lib/env.ts`, which runs `serverEnvSchema.parse(process.env)` at import. A missing `STORAGE_*`/`DATABASE_URL`/`BETTER_AUTH_SECRET` therefore aborts `trigger.dev deploy` with a zod error attributed to the task file. Set them in the environment (dashboard, or `POST /api/v1/projects/<ref>/envvars/<env>` with a `tr_pat_` token) *before* deploying. `BETTER_AUTH_SECRET` is required even though ingest never authenticates anything — the schema validates the whole server env, not the part this entrypoint uses.
- **The image build context is Trigger's bundle output, not the repo**, so a build extension cannot `COPY` a repo file into the image — it fails with "not found in the context". `additionalFiles()` puts files in the context but preserves the source tree layout, which is nested under the checkout's absolute path and therefore machine-dependent. `pinnedFfmpeg` in trigger.config.ts instead reads `scripts/check-ffmpeg-version.mjs` at config-evaluation time and base64-inlines its real bytes into the `RUN`, which keeps that script the single source of truth for `EXPECTED_MINOR` without restating what it checks. For real files there is a supported way in: writing into `manifest.outputPath` at config-eval time lands the file in the bundle output, which *is* the build context — that is how `additionalFiles()` works under the hood, and how `pinnedFfmpeg` ships the ffmpeg archive (in a dir named `pinned-ffmpeg`, because the context archiver silently drops `build`/`dist`/`out` names).
- **A hard-killed ingest is reaped, because it cannot clean up after itself.** `reapStalledIngests()` (lib/ingest-reaper.ts) marks a source failed when it still claims `processing` and nothing has written to the row for `INGEST_STALL_TTL_MINUTES` (lib/ingest-window.ts, 30). OOM, worker eviction, a timeout, or the in-process fallback dying with the dev server all skip `recordFailure`, so the row keeps a step that will never advance and an `ingest_error` of NULL — the UI shows "Preparing playback" forever, which is exactly what the first Trigger.dev run left behind. Scheduled like the upload sweep: from the project page's `after()`, only when that page's own query flagged a row via `isStalledIngest`. It is *silence*, not runtime — the ladder writes progress every 10s and the publish step does too, so a two-hour transcode never trips it; the window is sized for the steps that report nothing (thumbnails, audio, waveform). Deliberately scoped to `processing` and **not** `uploaded`: a queued row waiting on worker capacity or per-org concurrency is healthy, and failing those would break the queue rather than clean up after it. Erring long is the cheap direction — reaping early makes the row claimable while the original is still writing to it.
- Ingest runs through one seam: `enqueueIngest()` (lib/ingest.ts). With `TRIGGER_SECRET_KEY` set it triggers the durable Trigger.dev task (`trigger/ingest-source.ts`); without it the pipeline runs in-process after the response (dev fallback — dies with the server, documented, not for real workloads). Pipeline steps and their ffmpeg invocations live in `lib/media/`; the claim step makes re-enqueues and retries idempotent.
- Every artifact row carries its own `size_bytes`, written at upload time (`ArtifactUpload.sizeBytes` is required, not optional), and the artifacts `storage_bytes` ledger entry is **summed back out of those rows** inside the finalize transaction — one number, not a parallel tally that can drift. The single `hls_master` row accounts for the entire ladder (every playlist and segment under `hls/`), which is what makes that sum equal the real stored footprint; don't "fix" it to the size of `master.m3u8`. Both properties are asserted against the database in the ingest e2e — this is invisible in the UI, and `size_bytes` sat NULL on every row for a whole sprint without anything looking wrong.
- Upload resumability has **two independent halves, and the browser's half is destructible**. Golden Retriever restores the file list, source id and multipart state from localStorage/IndexedDB — the fast path — but files over 10 MB come back as ghosts, and dismissing that recovery card (or clearing site data, or switching browser) drops the state entirely. Re-adding the same file then opened a *second* multipart upload: observed on staging with the 2 GB exit-test source, which stranded 115 MB of parts under a duplicate row stuck at `uploading` while the UI promised the upload would carry on. So the server also matches on what it can see for itself — `findAdoptableUpload` (`lib/uploads.ts`): same project, filename and byte size, still `uploading`, and quiet for longer than `UPLOAD_ADOPT_GRACE_SECONDS`. That grace window is the guard against adopting an upload another tab is actively writing, and it works because `touchUpload` stamps `updated_at` on every signed part. Client-side adoption runs in an Uppy **pre-processor**, not a `file-added` handler: pre-processors are awaited before any uploader starts, so seeding `s3Multipart` (which is what puts `@uppy/aws-s3` on its `listParts` branch) always wins the race against a fast click. The same check also runs inside `POST /api/uploads`, so a duplicate row is unreachable rather than merely unlikely. Both paths are covered in `e2e/` — `upload-resume.spec.ts` for the browser half, `upload-adopt.spec.ts` for the server half — and the second one only proves anything with a fixture over 10 MB.
- Usage ledger (`usage_ledger`) is append-only **by policy shape**: it has only SELECT and INSERT RLS policies, so UPDATE/DELETE are database-denied even in-org. Writers must be idempotent via `correlation_id` (unique); corrections are compensating entries. Anything metered writes to the ledger in the sprint it ships — never retrofitted.
- Backfilling a metering column reads the **objects**, never the ledger: `pnpm backfill:artifact-sizes [--dry-run]` (scripts/backfill-artifact-sizes.ts) sizes historical artifacts from storage, org by org through `withOrgScope` so it needs no superuser and no policy exemption. It reports any source where the summed artifact bytes disagree with the ledger and writes nothing to `usage_ledger` — a correction there is a compensating entry, and a human's call.
- **One ffmpeg minor everywhere — 8.1.x — pinned in three places** (decision 2026-08-11). An ffmpeg option that doesn't exist is a *hard* failure: ffmpeg refuses to start and every ingest breaks. CI used to install Ubuntu's apt ffmpeg (6.1.1) while the image installs Alpine's (8.1.2), so CI could neither exercise the ffmpeg 8 behaviour `lib/media/` is written around nor accept an ffmpeg 8 flag — `-reconnect_max_retries`, verified on staging and macOS, died in CI with "Option not found" and was dropped to unblock (PR #23). The **image is the source of truth**: the Dockerfile runner pins the Alpine *release* (`node:24-alpine3.24`, not the floating `node:24-alpine`) because Alpine carries one ffmpeg minor per release for its whole life, and CI installs that same minor as a checksummed static build because no Ubuntu release ships it. **The static build downloads from this repo's own `ffmpeg-static/<build>` GitHub release, not from BtbN** (decision 2026-08-24): BtbN prunes dated autobuild releases after ~2 weeks, so the "pinned immutable" 2026-08-10 asset 404'd on 2026-08-24 and broke every e2e run — an upstream URL is provenance, not a home. `scripts/mirror-ffmpeg.mjs` re-hosts the exact tarball (verified against the upstream release's own `checksums.sha256`, round-tripped after upload) as a release asset only we can delete; the sha256 pin stays, and CI fetches with the workflow's `GITHUB_TOKEN` (`gh release download`). Weighed and rejected: BtbN's rolling `latest` release (stable URL, but the bytes change per rebuild — the sha256 pin, the actual integrity guarantee, is what it would cost); an R2 bucket (CI secrets or a public bucket, CI availability newly coupled to the Cloudflare account, and enabling public access is a dashboard-only step); pinning a BtbN *month-end* autobuild (those persist since 2024-09, but that's an undocumented retention courtesy from the third party that just burned us). GPL: the repo is private, so mirroring conveys nothing to the public — **if the repo ever goes public, the binary needs a corresponding-source offer first**; the release notes carry that rider. Enforcement is `scripts/check-ffmpeg-version.mjs` — it holds the expected minor and runs both in the CI e2e job and inside the Docker build, so whichever side drifts fails loudly; `pnpm check:ffmpeg` runs it on your machine. Rejected alternatives: running e2e inside the app image (it has no dev deps, and Playwright ships no musl browsers, so Alpine is a dead end), and `apk add ffmpeg=<exact>` (Alpine prunes superseded versions, so the pin breaks at the next patch bump).
- **Local-gate ffmpeg clarification (2026-08-29):** hosted-CI wording in the historical pin decision above explains why the mirror was created. The current local gate validates the machine's installed ffmpeg/ffprobe against 8.1.x; the private mirrored static archive remains load-bearing for the Trigger.dev image, whose remote builder cannot authenticate to GitHub itself.
- **Version-support rule for ffmpeg flags:** a new flag, filter or filter option may only be used if it exists in the pinned minor — check it against 8.1.x (`ffmpeg -h full`, or `docker run --rm node:24-alpine3.24 sh -c 'apk add -q ffmpeg && ffmpeg -h full'`), never against whatever your Mac happens to have. Moving to a newer ffmpeg is its own PR that bumps all three pins in one commit — `EXPECTED_MINOR` in the check script, the Alpine tag in the Dockerfile, and the mirrored static build (run `scripts/mirror-ffmpeg.mjs <btbn-tag> <asset>`, then paste the block it prints into `scripts/ffmpeg-pin.mjs`) — and re-runs the ingest e2e. Trigger.dev is covered by the same pin via `pinnedFfmpeg` (below); its bundled `ffmpeg()` extension (Debian apt 5.1.x) stays unused.
- **The ladder reports progress; every other step is short enough not to.** `-progress pipe:1` on the HLS ffmpeg run feeds a throttled write (10s) to `source.ingest_progress` (0–1, null when a step has nothing finer to say than its name), rendered as "Preparing playback 42%". A two-hour source spends ~30 minutes in that one step, and while it reported nothing the badge never changed *and* `updated_at` never moved — a healthy ingest was indistinguishable from a hung one in both the UI and the database, and got reported as stuck. Progress writes are best-effort and swallow their errors: a cosmetic signal must never fail a transcode. `parseProgressSeconds` reads `out_time_us` and deliberately ignores `out_time_ms`, which is microseconds too despite the name — matching it as milliseconds reports 1000× fast.
- **Trigger.dev gets the pinned ffmpeg too, via a custom build extension** (`pinnedFfmpeg` in trigger.config.ts). The bundled `ffmpeg()` extension installs Debian apt ffmpeg (5.1.x) and its only alternative is a floating git build; neither is the pinned minor. This is not cosmetic — `-reconnect_on_network_error` landed in 6.1, so the first thing setting `TRIGGER_SECRET_KEY` would have done is break every ingest on 5.1, on the runtime whose whole purpose is making ingest more reliable. The asset coordinates live in `scripts/ffmpeg-pin.mjs` and are consumed by both CI and the Trigger image; the deploy layer re-runs `check-ffmpeg-version.mjs` so a drifted pin fails the deploy, not the first upload. Since the pin moved to this private repo's own release (2026-08-24), the image build cannot download it — Trigger's remote builders hold no GitHub credentials — so config-eval on the deploying machine (which always has auth: `GH_TOKEN` in the deploy-trigger job, `gh auth login` for manual deploys) downloads and sha256-verifies the archive, writes it into the bundle output, and the layer bind-mounts it from the build context (`RUN --mount=type=bind` — a `COPY` would strand a ~120 MB dead layer in the final image). The checksum is re-verified in-image, so a corrupted context fails the deploy.
- ffmpeg 8 quirks encoded in `lib/media/`: mjpeg outputs need `format=yuvj420p` (limited-range YUV is rejected), and `fps=1/N` needs `:round=up` or sources shorter than N seconds emit zero thumbnails. Don't "clean up" those filter args.
- **Remote ffmpeg inputs go through `inputArgs()` (`lib/media/ffmpeg.ts`), and every transcode is duration-verified before it can reach `ready` (`lib/media/verify.ts`).** ffmpeg's HTTP reader treats a mid-transfer disconnect as end-of-file: it finalizes a **valid but truncated** output and exits 0, so with `-v error` nothing looks wrong anywhere. The exposure is read *duration*, not file size — the CPU-bound HLS ladder holds one connection open for the whole transcode (~28 min for a 2h source at 0.26× realtime, ~1.2 MB/s) while the audio step drains the same object in ~2 min and is unaffected. The S2 exit test produced a source marked `ready` carrying 4189s of 7200s of video (58.2%) on all three rungs, because probe had written the true 7200s to the row and nothing ever compared the two: the details pane read 2:00:00 from the database while the player read 69:48 from the playlist. Sources under ~5 minutes finish the read in seconds, which is why this survived all of S2. Never write a bare `-i url`, and never drop the duration assertions — reconnect flags lower the odds, the assertions are what keep a miss from reaching users silently.
- **Every video rung emits an I-frame-only companion playlist** (`v{n}/iframe/index.m3u8`, `#EXT-X-I-FRAMES-ONLY`), referenced from the master via `#EXT-X-I-FRAME-STREAM-INF` (whose presence bumps the master to `#EXT-X-VERSION:4`) — editor-study §5: keyframe-only filmstrip/scrub decode, which MediaBunny models directly (`hasOnlyKeyPackets`). Built per rung by `buildIframePlaylistArgs` (`lib/media/hls.ts`) as a **local** re-read of the just-verified rung output — `-skip_frame nokey` (only keyframes reach the decoder) + intra-only re-encode (`-g 1`, rung CRF) + `-fps_mode passthrough`, one tiny .ts per I-frame via `-hls_time 0`. Two 8.1.x traps, verified in the Alpine container, explain that shape: copy-mode `-hls_flags iframes_only` does **not** drop non-key packets (it only adds the tag — a playlist that lies), and `iframes_only+single_file` (Apple-style byteranges) writes every `#EXT-X-BYTERANGE` offset as `@0` in 8.1.2, producing undecodable ranges. EXTINF semantics: each entry is the gap to the next I-frame, but ffmpeg gives the *last* entry the frame's own duration instead of the distance to end-of-stream, so coverage checks (pipeline and e2e both) floor at duration − one keyframe interval. The iframe files live under `hls/`, so they fold into the `hls_master` row's `size_bytes` and the storage ledger automatically.
- Rendition ladder (`lib/media/hls.ts`) follows platform practice deliberately: native-resolution top rung (≤1080p, capped CRF per Apple's peak≤200%-of-average VOD rule, `fast` preset) over 720p/360p proxies, 2s keyframes, High profile, 1.5× caps for >40fps sources; the player starts at the top rung. The 234p–480p cellular rungs and multi-codec (VP9/AV1) are deferred until client delivery (S18) — don't add them to the review path.
- The source player (`components/sources/source-player.tsx`) is **Video.js v10 React** (`@videojs/react`, packaged `VideoSkin` + `HlsJsVideo`; hls.js is its internal engine — decision 2026-08-10, v8 is legacy/maintenance-only). Three hard-won rules, in its header comment — change them only with the e2e green: client-only mount (placeholder during SSR/hydration); peaks bound through a **passive `PlayerAdapter`**, never its default `MediaElementPlayer` (the engine attaches MediaSource at mount and StrictMode double-mounts it — `MediaElementPlayer.init` inspecting the element mid-churn either `load()`s a revoked single-use blob URL or rejects on a transient media error and hides the waveform; the adapter never loads and never inspects source state, so peaks-vs-engine ordering stops mattering and `src` needs no gating); and `playedWaveformColor` applied on `durationchange`, never at `Peaks.init` (peaks.js 4.0 freezes the played/unplayed boundary with the init-time duration — NaN before metadata — which left the whole strip permanently blank on load, identically in dev and production builds — reported upstream as [bbc/peaks.js#574](https://github.com/bbc/peaks.js/issues/574), so revisit this workaround when it is fixed). Startup quality rides `config.hlsJs.abrEwmaDefaultEstimate` (exceeds every ladder top rung → auto start level = top rendition); the config object must keep a stable identity or the engine reloads. The ingest e2e guards these: full-document-load for the SSR half, plus nonblank-pixel and played/unplayed-color assertions on the overview canvas — canvas *visibility* alone is not a render check and let the blank strip ship. Peaks.init additionally waits for the overview container to have layout (`waitForLayout`) — zero-width init (hidden tab, prerender) throws and used to hide the waveform permanently.
- Waveform peaks (`lib/media/peaks.ts`) must span the **media** duration, not the audio stream: sources whose audio ends early are padded with silent buckets, and `samples_per_pixel` scales with duration to target a ~4096px native width. Both are load-bearing for the overview timeline: peaks.js maps pixels to time through the data's implied duration and cannot upsample, so audio-length or too-short data desynchronizes the waveform x-axis from the video timeline (wide windows: truncated-looking waveform; narrow: playhead pegged early). Don't regress to a fixed `samples_per_pixel`.

## Transcription (S3 decisions)

- **Transcription is a follow-on job, not an eighth ingest step** (decision 2026-08-22): `ready` keeps meaning playable, a provider outage cannot fail a finished ingest, and the job has its own lifecycle (`transcript` row: pending → processing → ready | failed), reaper (`lib/transcription/reaper.ts`, silence-based like the ingest reaper, scoped to `processing` only — `pending` is a legitimate queue state), and retry. One seam: `enqueueTranscription()` — Trigger.dev task (`trigger/transcribe-source.ts`, no machine override; the provider does the heavy lifting) or in-process dev fallback, selected by `TRIGGER_SECRET_KEY` exactly like ingest. Called from `runIngestPipeline` after finalize, gated on `probe.audio`, errors swallowed there (the job records its own).
- **Provider seam is in-house; the AI SDK's `transcribe()` was evaluated and rejected** — its normalized output drops speaker labels and per-word confidence (the point of the integration) and it downloads-then-reuploads audio instead of handing the provider a URL. Adapters wrap the official SDKs: `@deepgram/sdk` v5 (`listen.v1.media.transcribeUrl`, nova-3, diarize/smart_format/detect_language) parses the **raw response with our own zod schema** because the SDK's generated types omit `speaker`/`punctuated_word`; a failed parse is a loud provider-contract alarm. `TRANSCRIPTION_PROVIDER=mock` is a deterministic fake for e2e/dev (the CI fixture has no speech); AssemblyAI lands behind the same interface with a cross-provider golden test. Provider env vars are raw `process.env` reads outside `serverEnvSchema` (the `TRIGGER_SECRET_KEY` precedent): unconfigured must degrade to "no transcript", never abort boot — but `DEEPGRAM_API_KEY` must be set in the Trigger environment or deployed transcriptions fail at run time.
- **Canonical transcript JSON lives in storage** (`{sourcePrefix}transcript/rev-N.json`), served through the existing `/api/media` org-prefix proxy; Postgres holds lifecycle + the revision ledger (`transcript_revision`, one row per stored JSON, `size_bytes` required). Deliberately **not** `source_artifact` rows: `claimSource()` deletes all artifacts on every re-ingest, which would silently discard paid transcriptions. Times are **integer milliseconds** end to end (`{text, startMs, endMs, confidence, speaker}` — the shape S8 caption derivation consumes; see docs/editor-study.md §1); speakers are string ids with display names in `transcript.speaker_labels` (a rename is metadata, never a new revision — revisions are reserved for changes to the words). Current revision = highest `revision`, no pointer column.
- **Metering**: `transcription_minutes` (media minutes, correlation `transcription:{sourceId}:{attempt}`) + `storage_bytes` with `category: "transcript"` per revision — full size, no delta arithmetic, because every revision is a new object, never an overwrite. The duration check on results is one-directional: words ending *after* the media (+2s slack) fail the run (wrong/corrupt object); a transcript ending early is legitimate speech silence, not S2-style truncation.
- SRT/VTT export and S8 caption pages build on **`@remotion/captions`** (plain MIT, zero deps — verified no exposure to the Remotion company license) plus our own speaker-aware segmentation; no library does speaker-aware cue breaks.
- **Speaker naming/merging is manual in S3 by design; AI takes it over in S4** (decision 2026-08-23, prompted by real over-segmented diarization on staging — one voice split across two ids). Diarization providers emit anonymous ids only; inferring names ("hosts introduce guests") and detecting same-person splits (semantic continuity across ids) is an LLM-over-transcript task that belongs to the S4 source-analysis capability — through the Mastra harness with tracing and evals (cross-cutting rule 2), never an ad-hoc S3 LLM call. It ships as **confirmed suggestions, not silent auto-apply** (wrongly merging two real people is worse than the split), and Apply drives the same `speaker_labels` action the manual dialog uses — the dialog is the actuator and the permanent human override, not a stopgap.

CTAs extraction was cut (its consumers are S11/S17); model-judged claim classification (`inference`/`unsupported`) is deferred to S11 — the grounding aligner assigns `direct_quote`/`paraphrase` deterministically for free; the extraction UI is one Highlights list with kind filters, not per-kind tabs. **Finding recorded for S6:** no ffmpeg silence/energy pass is needed for boundary snapping — inter-word gaps are pause detection and punctuated words are sentence boundaries; snap-to-sentence/pause derives from the word timeline (revises tech-stack §6.2's assumption).

The S4 gateway question is answered: still no gateway — one REST endpoint doesn't justify a hop, and the S4 disqualifiers stand. The compose swap moved alpine/musl → debian/glibc — a musl-initialized cluster reused under glibc risks silent collation corruption, so the dev volume was recreated (it is disposable by design). Neon supports pgvector natively.
- **Extraction is a follow-on job after analysis** (`source_extraction_run` + `source_extraction`, `lib/intelligence/extract-*`): four passes — quotes/stories/claims on sonnet, qa on haiku — over **one shared cached transcript prefix with ONE shared schema and system**. That sharing is load-bearing, not stylistic: Anthropic's cache key covers tools/output-format and system before messages, so a per-pass schema busts the cache that halves extraction cost; only the post-breakpoint instruction text may differ between passes, and the sonnet group primes with one awaited call before the rest run in parallel (caches are per-model). Assert `cache_read_input_tokens > 0` on non-prime passes in Langfuse (the standing caution). Automatic chain runs ONCE per source (`enqueueExtraction`, conflict-do-nothing); every re-run is a human action (`enqueueExtractionRerun` via the Highlights button) because re-extraction re-spends real model tokens.
- **The grounding aligner is the provenance gate** (`lib/intelligence/grounding.ts`, pure + heavily unit-tested): every extraction's claimed-verbatim `text` is fuzzy-matched to the word timeline near its claimed range, its range is SNAPPED to matched word boundaries (that is what makes surfaced ranges playable and exact), ungrounded rows persist with `grounded=false` for run stats but never surface, and repeated phrases resolve to the candidate nearest the claimed range. Claim classification is the aligner's byproduct, never model opinion: `direct_quote` when the statement is the span (token-multiset similarity ≥ 0.85), else `paraphrase` — the model-judged `inference/unsupported` values arrive with their S11 consumer, and the text enum extends without a migration. Q&A rows span question→answer (statement aligned in the 120s before the answer) while `speaker` stays the ANSWER's majority speaker; the model's own speaker/ms fields are never trusted, only used to steer the search window. Reused by design: S6 boundary snapping and S11 evidence links want exactly this text→time mapping.
- **Source Q&A is interactive and citation-verified** (`lib/intelligence/qa.ts` + `lib/ai/capabilities/source-qa.ts`): a server action (a human waits seconds; no lifecycle row, no reaper), retrieval = top-10 chunks by cosine within the source, and **every citation is deterministically clamped to a retrieved chunk's range before persisting** — the model cannot cite what retrieval didn't show it, which is what makes "playable timestamped evidence" hold by construction. `answerable=false` is a first-class outcome rendered as an explicit miss (own eval fixture), never an empty answer. Every ask persists to `source_question` (history UX + `qa:{id}:answer`/`qa:{id}:embed` ledger correlations + a growing real-question eval pool); searches meter their query embedding too (`search:{uuid}` — random correlation, every search is its own event). The golden Q&A eval retrieves in-memory with the production chunker so the runner needs no database.
- **Indexing is a follow-on job, not a transcription step** (`source_index` lifecycle + `transcript_chunk` rows, `lib/intelligence/`): chained from transcription success beside `enqueueAnalysis`, with its own silence-based reaper (processing-only, 10 min). Chunking is deterministic speaker-turn packing over `buildParagraphs` (~300-token windows, 30s-gap breaks, tail-merge) — pure and unit-tested; chunk `startMs/endMs` are what citations play, so boundary correctness is load-bearing. **Only the current revision's chunks are kept** and re-index replaces the set transactionally; unlike analysis, `enqueueSourceIndex` flips ready/failed rows back to pending by design (every new transcript revision re-embeds — fractions of a cent). Pre-S5 sources backfill opportunistically: the source page's render enqueues when its own query saw a ready transcript with a missing or revision-stale index (the reaper-scheduling pattern) — failed rows are deliberately NOT auto-re-enqueued (a permanent failure must not become a paid loop; retry is a human action — the source page renders a failed-index card whose retry button is `retryIndexAction`, filling the Ask slot so the failure is visible outside the Trigger dashboard, and the Voyage adapter retries transient 429/5xx with bounded backoff before a run may fail at all). Embedding spend is metered as `ai_tokens` with `metadata.kind = "embedding"`.

## Moment discovery (S6 decisions)

- **Discovery is a follow-on job after extraction** (`moment_discovery_run` + `moment_candidate`, `lib/intelligence/discover-*`): the automatic chain fires ONCE from extraction success (conflict-do-nothing), while every re-run is a human action. Dispatch intent is merged into `counts` as `dispatchState=pending` with a per-cycle `dispatchLease` before the external call; task claim, retry, stale-pending redispatch, stage writes, and final replacement must retain the exact lease/attempt without erasing the last committed result facts. Claims are pending-only and attempt-CAS protected, processing heartbeats every minute, and final persistence locks and verifies the active attempt before deleting old candidates, so a failed or retired worker cannot destroy reviewed moments. Every terminal failure path is candidate-aware: a failed first run becomes `failed`, while a failed refresh returns to usable `ready` with the error and old candidates/counts intact. ONE `generateStructured` pass on sonnet over a cached prefix (`lib/ai/capabilities/moment-discovery.ts`); if it ever splits into multiple passes they MUST share one schema and one system string (the S5 cache-key rule). Ledger correlation `discover:{sourceId}:{attempt}`.
- **The model proposes; pure code disposes** (`lib/intelligence/moments.ts`, client-safe): boundary snapping to the sentence grid (punctuated words = sentence boundaries, inter-word gaps ≥700ms = pauses — no ffmpeg pass, the S5 finding), anchor grounding through the S5 aligner (verbatim `anchorText` must align INSIDE the snapped range or the row persists `grounded=false` and never surfaces), dedupe, composite scoring, ranking. Snapping growth is capped at +10s per side (`SNAP_MAX_GROWTH_MS`) with pause-boundary fallback, then raw-bound fallback — a bad model range must not swallow extra audio. **Lead-in capture runs after snapping** (M1 review finding, 2026-08-25, Brett Lee source): the model anchors answer-shaped moments on the answer, so spans opened mid-exchange without the interviewer's question — `captureLeadIn` grows the start over the immediately preceding turn when it is by a DIFFERENT speaker, ≤20s long, and ≤3s away (a setup, not the other speaker's own moment); the prompt also instructs the model to start at the setup line, with the deterministic rule as the backstop. Speaker-turn starts are valid in-points in the eval grid for the same reason. `seedIds` are filtered to the extraction ids actually shown in the prompt; invented ids are dropped.
- **Dedupe is deterministic and two-pass**: range IoU > 0.5, then mean-chunk-vector cosine ≥ 0.92 for the "same story told twice apart" case. The cosine pass deliberately skips pairs with ANY range overlap (IoU's job) and pairs with identical chunk footprints — two short moments inside one chunk share a footprint vector by construction, and merging them collapses distinct beats, not duplicates (this is what keeps the 4s CI fixture from collapsing to one candidate). No index yet → cosine skipped, IoU still runs. Losers persist `suppressed=true` sharing `dedupe_group` with the keeper.
- **Composite = 0.3·hook + 0.25·insight + 0.25·relevance + 0.2·comprehensibility; risk is excluded** — it's a flag (`sensitive` at ≥0.6, badge in UI), never a demerit or exclusion. Weights are a named constant (`MOMENT_COMPOSITE_WEIGHTS`) to be retuned from M1 review data. Rank order: grounded survivors by composite, then suppressed, then ungrounded.
- **Cost levers (S6 checkpoint, 2026-08-25)**: sonnet extraction passes run `effort: "medium"` — thinking dominates output spend, the golden eval holds deterministic parity at medium, and budgets stay worst-case-sized (effort trims spend inside the allowance, never the ceiling). Claims-on-haiku was eval-tested and rejected: parity on the tiny fixture proves nothing against staging's content-dependent haiku grounding. Discovery stays at default effort until M1 passes — never cheapen the core bet before it's measured. Measured extraction cost is **length-sensitive**: fo547 (2.35h) ≈ $0.22–0.29/sh but Karma (0.73h) ≈ $0.76/sh, because per-pass output caps are absolute — judge $/source-hour on long sources, and expect short ones to look worse. The qa eval carries an LLM **citation-relevance judge** (key-gated) for the range-valid-but-irrelevant-citation failure mode. **First discovery model A/B (Brett Lee, 2026-08-26): opus was CHEAPER than sonnet** ($0.316 vs $0.33–0.42 per run) because it emitted 6.8k output tokens where sonnet emitted 16–22k — opus thinks less to reach a decision, so per-token price alone must never veto a tier audition; judge cost from the ledger's measured runs.
- **The cutting room is BUILT and ON BY DEFAULT (2026-08-28, docs/clip-cut-architecture.md Rounds 1–3 + shot grid in one PR, per Rajesh: no switches to remember).** Both clip jobs now run: persisted Director brief (`episode_brief` table, one row per source+revision — the cross-run memory for the button-triggered segment lane) → rough passes proposing PARAGRAPH-ID regions over ONE shared cached prefix/system/compact transport schema (`lib/ai/capabilities/episode-clips.ts`; `transcriptToPromptText` is no longer what clip passes read — they read `renderCoarse` from `lib/intelligence/grid.ts`) → per-clip CUTTER (`clip-fine.cut`, sonnet-medium, ±90s two-turn sentence-ID reel, `in≤payoff≤out` schema invariant, `couldNotFind` escape) → deterministic backstops (`lib/intelligence/grid.ts`: two-turn question-aware lead-in, lead-out trim, `stale_open`, pause-air, shot-snap; all recorded as flags in the new `moment_candidate.flags`/`segment_clip.flags`) → re-ground + re-dedupe (`dedupeAndRankMomentRows`) → cold Reviewer (DEFAULT ON — `MOMENT_REVIEWER=off` is the escape hatch; fix vocabulary grew `trim_start`/`extend_end`; inputs carry OPENS ON/CLOSES ON + lane rubric) → ONE bounded revision re-cut for boundary-class fixes (never re-reviewed, `revised`/`revision_rejected` flags). The episode passes force Anthropic's JSON response tool: native output-format could not compile the former four-mode grammar, while provider-stripped Zod constraints caused parseable output to die before deterministic repair. The small shared transport preserves the cache key; exact per-mode semantic schemas run locally and feed bounded repair. Segments: TOC-first rough contract, per-cut refinement seeing BOTH sides incl. drop text, `same_topic_neighbors` flag. Opus is now the TABLE default for both rough passes (the audition verdict, no env needed). Shot grid: `lib/media/shots.ts` writes a `shots` artifact at ingest (ffprobe scene scores on the lowest rung); absence degrades to no-op. Ledger correlations: `:brief`, `:cut`, `:revise` summed entries beside `:review`. Stage names JSONB-merge into run `counts` so the reapers' silence windows stay honest without erasing the last successful plan facts.
- **Segment boundaries are hypotheses, not mandatory cuts (decision 2026-08-28, Karma follow-up).** The post-#100 Karma run still produced 16 keeps, including direct question→answer and uninterrupted-explanation splits, because the Cutter could move every rough boundary but no component could remove one. The chapter lane is now: Director → rough ordered atoms → **global Opus Reconciler** (`segment-plan.reconcile`, same full-transcript cached prefix/system/transport schema) → Cutter over surviving boundaries → gauntlet → cold Reviewer. The rough pass is fail-closed: mode must match its sole non-null semantic branch, paragraph ranges must form an exact first-to-last cover with valid keep/drop packaging and one trimmed, non-empty TOC entry per keep, and one bounded repair receives the rejected plan plus exact errors. Reconciler output is an exact ordered cover of stable atom IDs; pure code rejects omission, duplication, reordering, non-contiguous grouping, keep/drop mixing, or missing packaging and falls back atomically. Anchor availability is provenance, never a topology constraint: code retains only candidates grounded inside their originating atom, then reselects one against the final post-Cutter slot; failure marks the keep `no_anchor` without changing its grouping. Final TOC is derived one-to-one from final keep groups. Duration is a soft suspicion signal only, never a quota. Cutter IDs outside their rendered reel and crossing parallel refinements are rejected instead of globally clamped. Cutter semantics follow the boundary type: KEEP→DROP starts discarded material after the payoff, DROP→KEEP starts at the kept setup, KEEP→KEEP requires a true topic turn, and DROP→DROP is never refined. If timestamp rounding gives an atom no audible slot, only that vacuous identity is folded away and flagged; it can never replace the audible KEEP/DROP side of a barrier. `segment_plan_run.counts.architectureVersion=2` invalidates old plans in the UI. Human edits operate on shared cuts: a nudge updates both neighbors atomically; merge unions adjacent keeps, resets stale review/decision state, preserves deleted-row provenance in `audit_log`, and marks metadata for review. `edit_version` protects nudges/restores/merges from silent reruns. A terminal re-plan failure is row-aware: if committed clips still exist, the run returns to `ready` with its error, old rows/reviews/edits and run facts remain visible, and only first-run failures become `failed`; successful finalization is the sole replacement point.
- **The Reviewer agent is COLD-context and advisory** (S6 §9, first slice of the editorial team — docs/episode-to-clips.md §9, method per docs/clipping-landscape.md): after the deterministic gauntlet, one small sonnet call per surviving candidate (`moment-review.verdict`) sees ONLY the clip's own span + title/hook — never the episode — and returns four 0–2 rubric scores (coarser and finer scales both judge inconsistently), a note, and ONE fix from a constrained vocabulary (`none|extend_start|trim_end|retitle|drop` — an unconstrained critic suggests impossible operations). Verdicts inform the human review (badge + note on flagged cards); they never move boundaries or hide candidates, a reviewer failure never fails discovery (columns stay null), and spend is one summed ledger entry (`discover:{sourceId}:{attempt}:review`). Default ON since 2026-08-28 (`MOMENT_REVIEWER=off` disables; mock analysis mode always reviews so CI proves the path). Calibration target: agreement with the human reviewer's decisions in the 75–80% band — the human-human ceiling — never higher.
- **Gate M1 MEASURED 2026-08-28: FAILED at 18% acceptance (3/17 vs the ≥70% bar) — on boundaries, not selection.** wrong_boundaries ×9 of 14 rejections; the two shapes are opens-on-previous-topic's-tail and closes-past-(or before)-the-payoff; raw→snap deltas were <3s, so the gauntlet is executing wrong narrative-level proposals faithfully; segments over-segment (26 keeps ≈100s median on 58min — beats, not topics). Root cause is structural: paragraph-level `[mm:ss]` stamps + free-form millisecond output means the model cannot address the timeline it cuts, and one monolithic pass holds finding+cutting+titling at once. The redesign — enumerated sentence-ID selection, a per-clip Cutter pass, deterministic narrative backstops (lead-out trim, stale_open, payoff invariant), lane identity by grid granularity, vision as shot-grid/frame-QC only (VLM boundary authority rejected on hour-scale grounding evidence) — is **docs/clip-cut-architecture.md** (this file's rules stand unchanged; rollout is one lever per M1 round, Cutter first). `pnpm moments:metrics --detail` is the boundary post-mortem view.
- **Human decisions are the M1 record**: accept/shortlist/reject (+reason enum) and boundary adjustments are first-class columns + audit entries. Every mutation increments the owning run's `edit_version` under a shared run lock. Because a successful re-run delete-and-replaces candidates, the first click submits the exact run id + attempt + edit version rendered beside those candidates; if any generation or edit changed, the server refreshes the page before it can issue a confirmation. Only an explicit destructive second submit may proceed, and only if that same token still matches after re-locking. Bare force flags and stale confirmations fail closed, boundary-only edits receive the same protection as decisions, and failed re-runs keep the old candidates usable. Acceptance rate and boundary-adjustment magnitude must each stay computable as one SQL query — `pnpm moments:metrics` (scripts/moment-metrics.ts) is the M1 readout that prints both, per source and overall. Boundary changes are additionally recorded in `audit_log` (`moment.boundaries_adjusted`, with before/after bounds); the action audit records what was authorized, while `moment_discovery.replaced` records actual discarded counts in the successful replacement transaction. Review UI: `components/sources/moments-panel.tsx` (registry primitives; card click plays with a 3s pre-roll, nudges walk the sentence grid client-side using the moments.ts helpers).

## Segment clips (S6.5 decisions)

- **The segment finder is the coverage lane beside moments' peak lane** (docs/episode-to-clips.md §1): `segment_plan_run` + `segment_clip` (migration 0012, RLS in-migration), an Opus rough partition (`segment-plan.partition`) followed by the global Reconciler decision above and the deterministic gauntlet in `lib/intelligence/segments.ts`. **Coverage holds by construction, not by trust**: surviving starts become cut points on the sentence grid (pause fallback, nearest-word last resort), cut points partition the word timeline into slots, uncovered leading stretches synthesize `gap_fill` drops, and a cut with no audible slot folds only that vacuous identity into its audible neighbor with a flag (never across a keep/drop barrier). Keep anchors ground through the S5 aligner; an anchorless keep is `grounded=false` + `no_anchor` flag, never auto-dropped.
- **No numeric editorial enforcement anywhere** (constraint policy 2026-08-26, generalizing the PR #90 count-anchoring finding): the prompt describes what a chapter IS and names no counts or durations; outliers are detected RELATIVELY (vs the plan's own median duration) and surface as flags (`short_outlier`/`long_outlier`), twice-told stories flag BOTH tellings via the chunk-vector cosine (`semanticTwinPairs`) — flags inform the human, nothing auto-demotes/splits/rejects. The eval scorer (`scoreSegments`) checks partition integrity and grounding, never durations.
- **Planning is a button, never a chain** (`dispatchSegmentPlan` via `planSegmentsAction` only): the plan heads toward spend-gated rendering, so the strategist chooses when. Dispatch intent is committed as `counts.dispatchState=pending` with a per-cycle `dispatchLease` before the external call and confirmed with its task id afterward; external completion, task claim, retry, and reaper redispatch must match that lease. The reaper redispatches only stale, unconfirmed intent, never a legitimately queued task. Claims are attempt-CAS protected, processing heartbeats every minute, and final persistence locks and verifies the exact active attempt, so duplicate or retired workers cannot spend twice or resurrect stale rows. Re-plans refuse while any segment carries a decision (the M1 contract); a model-proposed drop is restorable (`segment.restored` audit) — a proposal, never a veto. The cold Reviewer covers keeps with the same agent/flag/never-a-gate contract as moments (`reviewerEnabled`, one summed `segment:{sourceId}:{attempt}:review` ledger entry). `pnpm moments:metrics` reports both lanes.

## Tenancy and RLS (load-bearing security rules)

- Tenant-owned tables (anything with `organization_id`) get `ENABLE` + `FORCE ROW LEVEL SECURITY` and an org-isolation policy **in the same migration that creates them**, and an entry in `tests/rls-isolation.test.ts`.
- App code touches tenant tables **only** inside `withOrgScope()` (`lib/db/tenant.ts`), with the org id taken from `requireOrg()` — never from user input.
- The app's `DATABASE_URL` role must **never** be a superuser or table owner: superusers bypass RLS silently, and the Docker image's `POSTGRES_USER` is a superuser. The app connects as `mitosia_app`; `MIGRATE_DATABASE_URL` carries the owner connection used only by drizzle-kit and the container entrypoint. This applies to **CI too**: the e2e job creates `ci_app` (see ci.yml) — running the e2e app as the `ci` superuser silently disabled RLS and let a Playwright retry walk into a previous attempt's tenant (PR #16).
- Foreign-key checks do not consult RLS. Before inserting a child row, re-read the parent inside the org scope (see `assertVisible` in `lib/actions/hierarchy.ts`) so a cross-tenant parent id can never be attached.
- Tests: `TEST_DATABASE_URL` must point at a disposable database (the suite wipes it); run with `pnpm test`.

## UI (hard rule)

- **Never build UI components from scratch.** Before writing any UI, search the shadcn registry for an official component or block that fits (`pnpm exec shadcn add <name>`; blocks like `sidebar-07`, login/dashboard blocks, etc.) and adapt it. Composing registry primitives into domain components is fine; hand-rolling layout/navigation/form primitives that the registry already provides is not.
- **When adapting a registry block, keep its structural wrappers.** Base UI parts are context-coupled: `Menu.GroupLabel`/`DropdownMenuLabel` must stay inside a `Menu.Group`/`DropdownMenuGroup`, etc. Dropping a wrapper compiles fine and then crashes at runtime when the menu opens (e.g. "MenuGroupContext is missing"). This is exactly why the registry-first rule exists.
- **The source page is a two-pane workspace** (decision 2026-08-28, replacing the vertically stacked sections): player sticky in the left pane, review sections in a tabbed right sidebar (`components/sources/source-workspace.tsx`) — reviewing a clip must never require scrolling back to the video. All span playback goes through the workspace's single `useRangePlayback` instance: clicking a moment/segment/highlight/citation plays the span and **pauses at its out-point** (single-shot stop; any seek the hook didn't initiate — scrub, transcript word, chapter — disarms it, and a stop is never re-armed by resume). Tab panels are `keepMounted`, which is load-bearing: `data-transcript-status` and panel state must survive tab flips and poller refreshes. E2e consequences: click the `workspace-tab-*` trigger before asserting a panel visible (visibility needs the active tab; `toHaveText`/`toHaveCount`/attribute assertions work on hidden panels), and prove pause-at-out-point on a span whose end is strictly mid-media — a pause at media end proves nothing.
- **Interactive UI must be exercised by an e2e test.** Any menu, dialog, popover, or dropdown that can be opened gets a Playwright test in `e2e/` that opens it and asserts no `pageerror`. A visual/manual sweep is not sufficient — Base UI context crashes only fire on interaction. Run with `pnpm e2e` (dev server on 3001; `BETTER_AUTH_URL` must match that origin).
- **Two e2e suites, and they catch different things.** `pnpm e2e` runs against `next dev`; `pnpm e2e:prod` (`playwright.prod.config.ts`, `e2e-prod/`, port 3002) runs against the standalone production build via `scripts/serve-standalone.mjs` and needs a `pnpm build` first. If a dev server ran before that build, `rm -rf .next/dev` first: tsconfig includes `.next/dev/types/**`, and killing the dev server can leave generated files there half-written, failing the build with syntax errors in code nobody wrote. Dev mode cannot see hydration mismatches (React reports them as warnings, not the minified runtime error), and a mismatch shipped to production behind that gap. **Guard hydration and SSR behaviour by asserting on the server-rendered HTML**, not by sweeping for `pageerror`: mismatches are timing-dependent, and the sweep demonstrably passes on a build with the known regression restored while the SSR assertion fails immediately.
- **The exact-commit local gate uses two Playwright workers against isolated resources; ordinary ad-hoc local e2e stays `workers: 1` against the shared dev services** (decision 2026-08-29). Every spec provisions its own account + organization, so RLS and org-prefixed storage isolate workers. Keep e2e timeouts sized for a busy sibling worker (60s uploads/navigations, 30s signup redirects). Signup uniqueness must survive parallel worker processes: `Date.now()` + `process.pid` + counter (`e2e/support/auth.ts`) — don't drop a component. The gate sets `TRIGGER_SECRET_KEY=` and all three providers to `mock`, allocates free dev/prod ports, deletes `.next/dev` before `pnpm build`, and subjects both suites to a non-superuser role. It validates every commit including docs: predictable fail-closed behavior is worth more locally than maintaining a skip classifier. `next build` already runs the project-local `tsc` CLI over the complete tsconfig; do not restore an identical standalone typecheck unless Next's documented build behavior changes.
- The only exception is genuinely novel domain UI with no registry equivalent (e.g. the campaign canvas, transcript editor) — and even those must be built out of registry primitives wherever possible. Note the exception in the PR description when it applies.
- This registry uses the Base UI variant: composition is via the `render` prop, not `asChild`. Icons come from `@hugeicons/core-free-icons` (ESM-only — check names with an ESM import, not `require`).

## Conventions

- **Every process that talks to the database calls `tuneOutboundConnections()` (`lib/net-tuning.ts`) before its first connection** — `instrumentation.ts` for the server, the top of `main()` for `scripts/migrate.ts`. Node's Happy Eyeballs gives each resolved address 250ms, and the VPS is ~230ms from Neon's us-east-2 endpoint, so a normal TCP+TLS handshake gets abandoned as a false `ETIMEDOUT`; Neon also publishes AAAA records the container has no route to (`ENETUNREACH`). All six addresses fail in under a second and `pg` throws a bare `AggregateError`. It is set in code, not `NODE_OPTIONS`, so an environment that forgets it cannot silently produce a container that can never reach its database. Any new entrypoint that opens a database connection needs the same call — **including every file under `./trigger`**, because Trigger.dev workers run the task module directly and Next.js's `register()` hook never fires there (`trigger/ingest-source.ts` calls it at module scope, before the first query and not inside `run()`).
- The app role is provisioned by script, never by hand: `pnpm db:provision-app-role` (`PROVISION_DATABASE_URL` = owner, `APP_ROLE_PASSWORD` = the new role's password). It grants DML plus `ALTER DEFAULT PRIVILEGES` — miss the latter and the *next* migration produces tables the app cannot read — then asserts the role is not a superuser, lacks `BYPASSRLS`, and owns nothing, because all three disable RLS silently.
- The auth schema is generated: `pnpm db:auth:generate` (Better Auth CLI). Never hand-edit `lib/db/schema/auth.ts`.
- Schema changes ship as migrations: `pnpm db:generate` to author them, `pnpm db:migrate` to apply locally. No `drizzle-kit push` against shared databases.
- Deployed environments migrate themselves: `docker-entrypoint.sh` runs the bundled `scripts/migrate.ts` (advisory-locked, idempotent) before starting the server, and a failed migration aborts the container so the deploy fails loudly. Never run migrations during `docker build` — the image must stay environment-agnostic and build-time has no real database.
- `components/ui/**` is vendored shadcn registry output — lint-exempt (see biome.jsonc), regenerated via the shadcn CLI, not hand-maintained.
- `proxy.ts` performs optimistic redirects only. Authorization lives in server components and route handlers, never in the proxy.
